## 解決済み

| # | 論点 | 決定 | ADR |
| --- | --- | --- | --- |
| Q1 | 主対象ユーザーと中心利用シーンをどこに置くか | 主対象ユーザーは「作る人」。中心利用シーンは家庭での調理手順と記録。外部データ源はゼロ。食べ歩き・購入品比較は手動記録の付加機能に留める | [ADR-001](decisions/ADR-001-target-user-and-scope.md) |
| Q2 | 中心機能を1つに絞るなら何か | 中心機能は調理中の手順ガイド（タイマー内蔵）。焼き終わりに結果を1タップ記録し、次回起動時に前回条件を初期値提示する。記録は独立機能とせずガイド終端に組み込む。レシピ・配合管理は中心機能としない | [ADR-002](decisions/ADR-002-core-feature.md) |
| Q5 | 配信経路をどれにするか | 現フェーズは PWA（GitHub Pages・ホーム画面追加）。有料配布とサイドロードは将来の選択肢として残す。ADR-002 のタイマー要件を「前面表示＋Wake Lock で鳴る」に改定。記録のエクスポート／インポートを受入条件に含める。タイマー・通知・保存はポート抽象化 | [ADR-003](decisions/ADR-003-delivery-channel.md) |
| Q3 | 「前回条件の初期値提示」だけで再訪動機として足りるか | 足りない。記録の一覧・振り返り（読み取り専用）を足す。独立画面とせずガイド終端の記録の延長として配置。改善示唆・継続を促す仕掛けは現フェーズで採らない | [ADR-004](decisions/ADR-004-retention-design.md) |
| Q4 | ローカルに保持するデータの範囲とその境界 | 焼き記録1件は「設定値＋日時＋主観評価3択」。自由メモは持たない。条件ブロック（版番号付き・入れ子）と評価を分離。評価は提案ロジックへ結線しない。外部送信ゼロ、エクスポートは端末内共有シートのみ。日時は UTC 保存・表示時変換 | [ADR-005](decisions/ADR-005-record-schema.md) |
| Q11 | 評価3択の語彙をどう定義するか | 「激うま」／「うま」／「まぁまぁ」。※会議を経ず人間が直接裁定 | [ADR-006](decisions/ADR-006-rating-vocabulary.md) |
| Q7 | 初回起動から中心機能到達までの導線 | レシピを複数件同梱し、選んで指示どおり作れば美味しく作れる状態にする。一般的な餃子に加え作り手の興味をそそる餃子を含める。初回に条件入力を課さない。※会議を経ず人間が直接裁定 | [ADR-007](decisions/ADR-007-onboarding-and-recipes.md) |
| Q10 | 端末権限をどこまで使い、拒否時どう振る舞うか。記録に写真を含めるか | 現フェーズは権限を一切要求しない。写真は記録に含めず通知権限も要求しない。報知は音とバイブのみ。将来写真を追加する場合は別エンティティ参照として外付けし、新規 ADR を要する | [ADR-008](decisions/ADR-008-device-permissions.md) |
| Q10再 | 報知手段（ADR-008 再審議） | バイブは iOS Safari で実装不可能なため削除。報知は音と満了時の全画面視覚報知の2つ。音・視覚の2出力を持つ単一ポートとし prime() を定義。消音検知は不可能なため行わず、開始前に一文だけ警告。必須受入条件は「満了時に画面が規定状態へ遷移」、音は実機チェックリストの必須項目として別立て | [ADR-012](decisions/ADR-012-notification-means.md) |
| Q6 | オンライン機能を入れるか。付加価値の境界はどこか | 機能としてのオンライン要素は入れない。通信は本体の配信・更新のみ（オンライン機能に数えない）。記録の共有・端末間移送もレシピの追加取得も入れない。レシピ増補は本体更新に同梱。同梱レシピは版番号付き静的データとしてコードから分離し読込をポート化 | [ADR-009](decisions/ADR-009-online-boundary.md) |

| Q9 | MVP の完了をどう定義するか | 必須／推奨の二分。必須は機能条件5点＋構造条件4点＋同梱レシピ3件（変わり種1、手順数を変える）。検証は画面内ログ表示で代替。spec.md には推奨枠も必須／推奨の区別を付けて記載する | [ADR-011](decisions/ADR-011-mvp-definition-of-done.md) |

## 決定に付随する制約（論点ではないが後続を縛る）

| 出所 | 制約 |
| --- | --- |
| ADR-001 / architect | レシピ・手順をコードに直書きせず、データ層と表示層を分離すること（フェーズ3のアーキテクチャ決定で担保する） |
| ADR-001 / builder | レシピ内容の作成は実装外の執筆工数。Q9（MVP完了定義）で工数として明示的に見積もること |
| ADR-002 / architect | 次回条件の提案ロジックを記録スキーマから分離すること |
| ADR-002 / qa-sec | バックグラウンド復帰時の進行位置とタイマー挙動を受入条件に明記すること（Q9） |
| ADR-002 / builder | タイマーのバックグラウンド動作が配信経路の必須要件（Q5）。PWA は脱落しうる |
| ADR-003 / architect | タイマー・通知・保存はポートとして抽象化し、Web を一実装に留める（将来のネイティブ殻載せ替えのため） |
| ADR-003 | 「画面を離れると鳴らない」は仕様。不具合として扱わず、調理開始前にユーザーへ明示する |
| ADR-004 / architect | 記録一覧は読み取り専用ビュー。独立画面化せず、ガイド終端の延長として配置する |
| ADR-012 / architect | 報知は音・視覚の2出力を持つ単一ポート。ユーザー操作時の `prime()` をポートに定義し、AudioContext を呼出側へ漏らさない |
| ADR-012 | 開始前の消音警告は**1回・一文まで**。これを超える説明を置かない（成功条件2 を損なわないため） |
| ADR-012 | `AudioContext.resume()` を経ずにタイマーが開始する経路がゼロであることを静的確認と実機で担保する |
| ADR-011 | **/spec は推奨枠の条件も受入条件として記載し、必須／推奨の区別を明示すること**（推奨枠が仕様書から消えるのを防ぐ） |
| ADR-011 | 検証は画面内ログ表示で代替する（Windows から Safari 実機デバッガを使えないため） |
| ADR-010 / architect | 記録に不変ローカル ID を持たせる（ADR-005 のスキーマに追加。識別子のみを目的とし、報酬・継続・示唆には当たらない） |
| ADR-010 | マージの採用には新規 ADR を要する。その際 不変ローカル ID を同一性判定の基準とし衝突解決規則を受入条件に含めること |
| ADR-009 / architect | 同梱レシピは版番号付き静的データとしてコードから分離し、読込をポート化する（ADR-001 の architect 条件の具体化） |
| ADR-009 | レシピの追加取得を将来足す場合は新規 ADR を要する。その際 取得失敗・部分ダウンロード・改竄レシピの受入条件とキャッシュ系統の整合を含めること |
| ADR-008 | 写真の追加には新規 ADR を要する。その際 EXIF 除去・容量上限・往復検証の成立条件を受入条件に含めること |
| ADR-005 / qa-sec | 評価3択を示唆ロジックへ結線する変更は ADR-004 の C 不採用の迂回に当たる。**新規 ADR を要する** |
| ADR-005 / architect | 条件ブロックは版番号付きの入れ子。フラット列にしない（餡・皮追加時のインポート互換のため） |
| ADR-004 / qa-sec | 改善示唆（C）・継続を促す仕掛け（D）には拒否権が立っている。再浮上させる場合は受入条件を書けることを示したうえで再審議する |

## 現フェーズの受入条件にしない事項

charter r3 により、目的1「多くのユーザーに長い時間」は**ソフトウェアの中身の魅力**によって達成される事柄であり、
非機能要件ではない。受入条件として数値化しない。

- ADR-001 の未解消リスク「作る人は母数が狭い」は、目的1の性質上、現フェーズでは受入条件にしない。
  プロトタイプに対する知り合い数名の評価をもって判断材料とする。
