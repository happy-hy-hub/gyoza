## 未決

| # | 論点 | なぜこの優先度か |
| --- | --- | --- |
| Q10 | **端末権限（写真・カメラ・通知）をどこまで使い、拒否された場合どう振る舞うか** | ADR-001 派生。ADR-002 により写真は必須でなくなり、**記録に写真を含めるか**が争点になる。タイマー通知の権限もここで扱う。**ADR-005 により記録は3要素構成で確定済み**。写真を含める場合はその構成への追加として扱う |
| Q6 | **オンライン機能を入れるか。入れるなら「付加価値」の境界はどこか** | charter が「通信は付加価値に留める」とした線引きの具体化。**ADR-005 で外部送信ゼロが確定**したため、記録データの送信を伴うものは検討対象から除外済み |
| Q11 | **評価3択の語彙をどう定義するか** | ADR-005 派生。「良かった／普通／失敗」は会議での例示であり未決定。3体が独立に「死に票化」「評価者ごとに意味が割れ解釈不能」をリスクに挙げた。**死に票化すると ADR-004 の一覧の価値が消える**ため、UI 文言ではなく再訪動機の成否に関わる |
| Q7 | **初回起動から中心機能到達までの導線をどう設計するか（記録0件の空状態を含む）** | 成功条件2 の実現手段。ADR-003 により導入は「URL を開く→ホーム画面に追加」。**ADR-004 により記録0件が初回の既定状態**。「一覧が空疎に見える／ログ羅列に留まる」リスクをここで扱う |
| Q8 | **エクスポート／インポートの形式・粒度・操作 UX をどうするか** | ADR-003 で「実装すること」、**ADR-005 で「端末内の共有シートのみ」**が決定済み。残るのは形式の具体・粒度・操作 UX。形式は版番号付き条件ブロックを往復できること |
| Q9 | **MVP の完了をどう定義するか（受入条件の粒度と検証手段）** | 全論点の決定を受けて最後に締める。実機デバッグ手段の確定を含む。**ADR-003**: 前面表示でタイマーが鳴り切る／画面を離れると鳴らない（仕様として合格扱い）／復帰時に経過時間を再計算し進行位置を復元／エクスポートとインポートが往復で成立する。**ADR-004**: 初期値の3ケース（記録あり→前回値／記録ゼロ・消去後→既定値／インポート後→復元）、前回値の残骸が混在しないこと、記録0件時の一覧表示。**ADR-005**: 保存値＝再表示値＝エクスポート値の往復一致（値域有限を利用し全ケース検証）／日時の UTC 保存・表示時変換（タイムゾーンをまたいでも記録順が壊れない）／版番号の異なる記録のインポート互換 |

## 解決済み

| # | 論点 | 決定 | ADR |
| --- | --- | --- | --- |
| Q1 | 主対象ユーザーと中心利用シーンをどこに置くか | 主対象ユーザーは「作る人」。中心利用シーンは家庭での調理手順と記録。外部データ源はゼロ。食べ歩き・購入品比較は手動記録の付加機能に留める | [ADR-001](decisions/ADR-001-target-user-and-scope.md) |
| Q2 | 中心機能を1つに絞るなら何か | 中心機能は調理中の手順ガイド（タイマー内蔵）。焼き終わりに結果を1タップ記録し、次回起動時に前回条件を初期値提示する。記録は独立機能とせずガイド終端に組み込む。レシピ・配合管理は中心機能としない | [ADR-002](decisions/ADR-002-core-feature.md) |
| Q5 | 配信経路をどれにするか | 現フェーズは PWA（GitHub Pages・ホーム画面追加）。有料配布とサイドロードは将来の選択肢として残す。ADR-002 のタイマー要件を「前面表示＋Wake Lock で鳴る」に改定。記録のエクスポート／インポートを受入条件に含める。タイマー・通知・保存はポート抽象化 | [ADR-003](decisions/ADR-003-delivery-channel.md) |
| Q3 | 「前回条件の初期値提示」だけで再訪動機として足りるか | 足りない。記録の一覧・振り返り（読み取り専用）を足す。独立画面とせずガイド終端の記録の延長として配置。改善示唆・継続を促す仕掛けは現フェーズで採らない | [ADR-004](decisions/ADR-004-retention-design.md) |
| Q4 | ローカルに保持するデータの範囲とその境界 | 焼き記録1件は「設定値＋日時＋主観評価3択」。自由メモは持たない。条件ブロック（版番号付き・入れ子）と評価を分離。評価は提案ロジックへ結線しない。外部送信ゼロ、エクスポートは端末内共有シートのみ。日時は UTC 保存・表示時変換 | [ADR-005](decisions/ADR-005-record-schema.md) |

## 決定に付随する制約（論点ではないが後続を縛る）

| 出所 | 制約 |
| --- | --- |
| ADR-001 / architect | レシピ・手順をコードに直書きせず、データ層と表示層を分離すること（フェーズ3のアーキテクチャ決定で担保する） |
| ADR-001 / builder | レシピ内容の作成は実装外の執筆工数。Q9（MVP完了定義）で工数として明示的に見積もること |
| ADR-002 / architect | 次回条件の提案ロジックを記録スキーマから分離すること |
| ADR-002 / qa-sec | バックグラウンド復帰時の進行位置とタイマー挙動を受入条件に明記すること（Q9） |
| ADR-002 / builder | タイマーのバックグラウンド動作が配信経路の必須要件（Q5）。PWA は脱落しうる |
| ADR-003 / architect | タイマー・通知・保存はポートとして抽象化し、Web を一実装に留める（将来のネイティブ殻載せ替えのため） |
| ADR-003 | 「画面を離れると鳴らない」は仕様。不具合として扱わず、調理開始前にユーザーへ明示する |
| ADR-004 / architect | 記録一覧は読み取り専用ビュー。独立画面化せず、ガイド終端の延長として配置する |
| ADR-005 / qa-sec | 評価3択を示唆ロジックへ結線する変更は ADR-004 の C 不採用の迂回に当たる。**新規 ADR を要する** |
| ADR-005 / architect | 条件ブロックは版番号付きの入れ子。フラット列にしない（餡・皮追加時のインポート互換のため） |
| ADR-004 / qa-sec | 改善示唆（C）・継続を促す仕掛け（D）には拒否権が立っている。再浮上させる場合は受入条件を書けることを示したうえで再審議する |

## 現フェーズの受入条件にしない事項

charter r3 により、目的1「多くのユーザーに長い時間」は**ソフトウェアの中身の魅力**によって達成される事柄であり、
非機能要件ではない。受入条件として数値化しない。

- ADR-001 の未解消リスク「作る人は母数が狭い」は、目的1の性質上、現フェーズでは受入条件にしない。
  プロトタイプに対する知り合い数名の評価をもって判断材料とする。
