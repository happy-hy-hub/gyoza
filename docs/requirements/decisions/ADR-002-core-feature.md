# ADR-002: 中心機能の決定

- 日付: 2026-09-10
- 状態: 採択（**一部改定あり: ADR-003**）
- 改定: タイマー要件「バックグラウンドで鳴ること」は [ADR-003](ADR-003-delivery-channel.md) により
  「**前面表示＋Wake Lock で鳴ること**」に改定された。本 ADR のその記述は effective ではない。

## 論点

ADR-001 で確定した「家庭での調理手順と記録」という枠内で、中心機能を1つに絞るなら何か。
候補は A「調理中の手順ガイド」、B「焼き記録とチューニング」、C「レシピ・配合の作成管理」。
会議では A 3体・B 2体に立場が割れ、C は5体全員が中心機能から退けた。

## 決定

中心機能は**調理中の手順ガイド**とする。火加減・蒸し・仕上げを1画面ずつ進め、タイマーを内蔵する。

焼き終わりに**結果を1タップで記録**する。記録は**独立機能とせず、ガイドの終端に組み込む**。

**次回起動時に、前回の条件を初期値として提示する。**

**レシピ・配合の作成管理は中心機能としない。**

## 理由

- 人間の裁定による。
- A 派（builder / qa-sec / user-advocate）の根拠: 静的手順＋画面送り＋タイマーで永続化がほぼ不要なため
  charter 成功条件1（オフライン完走）を最小工数で満たせる。状態遷移が有限で受入条件を書ける。
  調理中に手が塞がった状態で「次に何をするか」を出すことが、その場で使う人が得をする唯一の形である。
- B 派（pm / architect）の根拠: 蓄積型のみが charter 目的1（長時間利用）と成功条件3（再訪理由）に直接寄与する。
  記録は追記型エンティティで他に依存しないため、後から手順・レシピを上に載せられる。
- 両者は排他ではない。記録を独立機能ではなくガイドの終端に置くことで、A の「再訪動機が弱い」という欠点と
  B の「初回起動がデータゼロで空振りする」という欠点を同時に解消できるため、この形を採った。

## 却下した案とその理由

- **A 単独（記録を持たない手順ガイド）**: 一度使えば終わりで再訪動機がなく、charter 目的1・成功条件3 を満たせない。
  pm が指摘したとおり、蓄積がなければ「長い時間使ってもらう」に寄与しない。
- **B を中心機能に据える案**: 初回起動時にデータがゼロで価値が出ず、成功条件2「説明なしで中心機能に到達」が
  空振りする。また qa-sec が指摘したとおり「次回提案」の正解が定義できず受入条件を書けない。
- **B を独立機能として並置する案**: 機能が2つに割れ、初回起動時にどちらへ進むべきかが不明瞭になる。
  user-advocate の条件に従い、ガイドの終端に組み込む形とした。
- **C（レシピ・配合の作成管理）を中心に据える案**: 5体全員が独立した理由で退けた。再訪動機が弱い／後付け可能／
  改訂履歴（版管理）のデータモデル工数が数倍／調理中の利益が説明できない。中心機能から除外する。

## 影響範囲

- **Q3（再訪動機）**: 再訪動機の中核は「前回条件の初期値提示」に確定した。Q3 はこれで十分かを検証する論点になる。
  ADR-001 の未解消リスク（「作る人」は母数が狭い）は Q3 に残る。
- **Q4（ローカルデータ範囲）**: 保持データは (1) 手順定義（静的）と (2) 焼き記録（追記型）の2種。
  architect の条件により、**次回条件の提案ロジックは記録スキーマから分離する**こと。
  また記録スキーマは焼き条件のみに特化させず、将来 C（餡・皮）を追加する際に全面改訂とならない形にする。
- **Q10（端末権限）**: ガイド中心のため、写真は必須ではなくなった。記録に写真を含めるかが Q10 の争点になる。
- **Q5（配信経路）**: ~~タイマーがバックグラウンドで鳴ることが配信経路の必須要件になった。~~
  → **ADR-003 で決着**。PWA を採用し、タイマー要件を「前面表示＋Wake Lock で鳴る」に改定した。
- **Q7（初回起動の導線）**: 初回起動の到達先は手順ガイドである。記録ゼロ状態でも成立する。
- **Q9（MVP 完了定義）**: qa-sec の条件により、**バックグラウンド復帰時の進行位置とタイマー挙動**を
  受入条件に明記すること。「全手順を通し画面遷移完了」が受入条件の基本形になる。
- レシピ・配合の管理は以後、中心機能候補として再浮上させない（再検討する場合は新規 ADR を要する）。
