# ADR-003: 配信経路の決定と ADR-002 のタイマー要件改定

- 日付: 2026-09-11
- 状態: 採択
- 改定対象: ADR-002（タイマー要件を改定する）

## 論点

現フェーズの配信経路をどれにするか。charter r3 の制約4（追加料金ゼロ）・制約5（現フェーズはプロトタイプ、
評価者は知り合い数名。ただし後の広い配布を構造的に閉ざさない）のもとで、
PWA／無料 Apple ID サイドロード／有料配布を比較した。
本論点は一度審議したが、charter が r2 → r3 に改訂され前提が変わったため再審議している。

## 決定

現フェーズの配信経路は **PWA**（GitHub Pages 配信・ホーム画面追加）とする。
有料配布とサイドロードは現フェーズでは採らず、**将来の選択肢として残す**。

**ADR-002 の「タイマーがバックグラウンドで鳴ること」を改定し、「前面表示＋Wake Lock で鳴ること」とする。**
**画面を離れると鳴らないことを仕様として明示する**（不具合ではなく仕様である）。

**記録のエクスポート／インポートを現フェーズの受入条件に含める。** ストレージ消去時の復旧手段とする。

**タイマー・通知・保存はポートとして抽象化し、Web を一実装に留める。**

## 理由

- 人間の裁定による。
- 制約4と制約5を同時に満たすのは PWA のみである。サイドロードは無料だが、
  評価者各人に7日ごとの再署名を課すため、制約5後段「各人の端末で無理なく使い続けられる導入方法」に反する。
- 現フェーズの目的は数名から**プロトタイプの評価を得ること**である。導入が面倒な経路を採ると、
  評価がアプリの中身ではなく導入手順に対して返ってきてしまい、フェーズの目的自体を損なう。
- qa-sec は「Safari のストレージ消去が非決定的で受入条件が書けない」として拒否権を行使し C を主張した。
  この拒否理由は「消去されること」ではなく「**非決定的で条件化できないこと**」にある。
  よって消去を仕様上の前提として認め、**エクスポート／インポートという復旧手段を受入条件に加える**ことで、
  拒否の根拠そのものを解消する形を採った。
- architect の条件（ポート抽象化）を採用することで、制約5の「後の広い配布を構造的に閉ざさない」を担保する。
  将来ネイティブ殻へ載せ替える際、タイマー・通知・保存の実装を差し替えるだけで済む。

## 却下した案とその理由

- **C（ネイティブ + 無料 Apple ID サイドロード）**: 7日ごとの再署名を評価者各人に強い、期限切れで起動不能になる。
  制約5後段に反する。また Windows 開発・Xcode 無し（制約1）のため、macOS ランナー CI・署名・SideStore 導入と、
  配信基盤の工数が中心機能本体を上回る。qa-sec のみが支持したが、その根拠は上記のとおり別手段で解消した。
- **B（ネイティブ + Apple Developer Program 年約$99）**: 制約4（追加料金ゼロ）に反するため検討対象外。
- **A 単独（PWA を採るが ADR-002 のタイマー要件を維持する）**: iOS の PWA はバックグラウンドで JS タイマーが
  動かず、Web Push はサーバ必須で非目標2・目的2と衝突する。要件を満たせないまま実装に入ることになり、
  qa-sec の指摘どおり合否判定が不能になる。要件側を改定する形を採った。
- **バックグラウンド通知を維持するため制約4（無料）を外す案**: 人間の裁定により制約4は必須。

## 影響範囲

- **ADR-002 を改定する。** 中心機能（調理中の手順ガイド）と記録の組み込みは維持。
  タイマー要件のみ「バックグラウンドで鳴る」→「前面表示＋Wake Lock で鳴る」に変更する。
- **Q8（データ移行・エクスポート）の一部が先行決定した。** エクスポート／インポートは現フェーズの受入条件である。
  Q8 に残るのは「形式・粒度・移行操作の UX」に限られる。
- **Q4（ローカルデータ範囲）**: 保存はポート越しに行う。Safari ストレージ消去を前提とした設計とする。
- **Q9（MVP 完了定義）**: 受入条件に以下を含める。
  - 前面表示のままタイマーが最後まで鳴ること
  - 画面を離れた場合に鳴らないこと（仕様として合格扱い）
  - 復帰時に経過時間を再計算して進行位置を復元すること
  - 記録のエクスポートとインポートが往復で成立すること
- **Q7（初回起動の導線）**: 導入は URL を開いてホーム画面に追加する経路になる。この手順自体も導線に含まれる。
- **実装方針**: タイマー・通知・保存は Service Worker や Web API に直接依存させず、ポート越しに使う。
  Web 実装はその一実装に留める（architect の条件）。
- **フェーズ2 の技術調査に検証項目が2件発生した**（下記）。**いずれも本決定の前提であり、
  結果によっては本 ADR の再審議を要する。**
  1. ホーム画面に追加した PWA のストレージが、どの条件で OS に消去されるか。
     （qa-sec の拒否根拠がこの事実に依存している）
  2. iOS Safari の Screen Wake Lock API が実機で安定して機能し、前面表示のままタイマーが鳴り切るか。
     （不成立の場合、タイマー要件と配信経路の両方を再審議する）
