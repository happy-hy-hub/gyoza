# ADR-001: 主対象ユーザーと中心利用シーンの決定

- 日付: 2026-09-10
- 状態: 採択

## 論点

このアプリの主対象ユーザーをどこに置くか。候補は A「作る人」（家庭での調理）、B「食べ歩く人」（外食・食べ歩き記録）、C「購入品を比較する人」（市販品・購入品の比較記録）の3方向があり、どれを中心に据えるかで中心機能・データ範囲・配信経路の以後の論点すべてが変わる。

## 決定

主対象ユーザーは餃子を**「作る人」**とする。中心利用シーンは**家庭での調理手順と記録**に置く。
外部データ源は**一切持たない**（レシピDB連携・店舗情報・価格情報などの外部参照はゼロ）。
B（食べ歩き記録）・C（購入品比較）の要素は、中心機能としては採用せず、**ユーザーが手動で記録する付加機能**としてのみ残す。

## 理由

- 人間の裁定による。
- charter の目的2「オンラインに依存せず、ローカル単体で機能が成立する」・制約3「データはローカル保持が既定」と最も整合するのが「作る人」中心のシナリオである。調理手順・記録は本質的にユーザー自身が入力するデータで完結し、外部データ源を必要としない。
- B・Cを中心に据える場合、店舗情報や価格情報など何らかの外部データとの突き合わせが実用上期待されやすく、オフライン単体成立という目的2の制約と衝突しやすい。中心機能から外すことでこの衝突を未然に回避する。

## 却下した案とその理由

- B「食べ歩く人」を中心に据える案: 食べ歩き記録は店舗・メニューなど外部世界の情報と結びつきやすく、外部データ源ゼロの方針や オフライン単体成立という charter の目的2と相性が悪い。中心機能ではなく手動記録の付加機能として残す。
- C「購入品を比較する人」を中心に据える案: 購入品比較は価格・商品情報など外部データに依存しがちで、Bと同様の理由により中心機能化を見送る。手動記録の付加機能として残す。
- 外部データ源（レシピAPI・店舗API・価格情報など）を何らかの形で持つ案: 「外部データ源ゼロ」の明示的な裁定により却下。将来オンライン機能を検討する余地は Q6 に残すが、少なくとも中心機能としては不採用。

## 影響範囲

- Q2（中心機能）: 家庭調理の手順・記録に関する機能に候補を絞り込む。食べ歩き・購入品比較を主機能候補から除外する。
- Q4（ローカルデータ範囲）: 保持データは調理レシピ・手順・調理記録が中心となり、店舗情報や価格情報など外部由来のデータ構造は不要になる。
- Q5（配信経路）: 外部データ源との通信が不要なため、オフライン単体で完結する構成を前提に選択肢を評価できる。
- Q6（オンライン機能の境界）: 「付加価値」の範囲は、レシピ・調理データそのものではなく、手動記録の共有・バックアップなど周辺機能に限定される方向で検討する。
- 以後の論点で「食べ歩き」「購入品比較」への言及があれば、常に「手動記録の付加機能」という位置づけであることを前提にする。
