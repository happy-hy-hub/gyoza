# ADR-011: MVP の完了定義と検証手段

- 日付: 2026-09-11
- 状態: 採択

## 論点

何をもって MVP 完了とするか。ADR 7本（003・004・005・007・008・009・010）から受入条件が約20項目
積み上がっている。受入条件の粒度、同梱レシピの件数（ADR-007 から9本持ち越された未見積り分）、
および Windows 開発・iPhone 実機という制約下での検証手段を決める。

## 決定

**MVP 完了は「必須」と「推奨」の二分で定義する。**

### 必須（これを満たせば MVP 完了）

**機能条件**

1. 機内モードでの中心機能完走（同梱レシピの選択から手順完走・記録まで）
2. エクスポート／インポートの往復が全ケースで一致すること
3. 版番号・スキーマの検証に失敗したファイルで、既存データが無変化であること
4. インポート実行前に、消去される件数が提示されること
5. 権限 API 呼出がゼロであること

**構造条件**（実装の作り方の縛り。遡及できないため必須側に置く）

6. タイマー・通知・保存のポート抽象化（ADR-003）
7. 記録の版番号付き条件ブロック構造（ADR-005）
8. レシピのデータ分離と読込のポート化（ADR-009）
9. 記録の不変ローカル ID（ADR-010）

**同梱レシピ**

10. **必須3件。変わり種1件を含む。手順数を変える**（データ構造の可変性を示すため）

### 推奨

上記以外の受入条件はすべて推奨とする。**既知の欠落として評価者に伝える。**

### 検証手段

- **検証は画面内ログ表示で代替する。** Windows から Safari 実機デバッガを使えないため（charter 制約1）。
- 検証不能だった条件を、次のとおり書き換える。

| 元の条件 | 書き換え後 |
| --- | --- |
| 権限ダイアログが一度も表示されない | 権限 API 呼出ゼロ（grep）＋実機で未要求のまま完走 |
| ストレージ消去後にインポートで復元される | **Safari 手動消去で再定義**（V1 未検証のため） |
| SW 更新後に旧版と新版のレシピが混在しない | レシピ版番号を画面表示させて判定 |
| 機内モードで最初から最後まで通る | 実機手動チェックリスト |

### /spec への指示

**spec.md には推奨枠の条件も受入条件として記載し、必須／推奨の区別を明示する。**

## 理由

- 人間の裁定による。**5体全員が B（必須／推奨の二分）で立場一致**した。
- 必須枠を qa-sec の案（拒否権由来の項目で固定）に置いたのは、それらが「受入条件が書けない」という
  拒否権の根拠に直接対応する項目だからである。
- **構造条件4点を必須に加えたのは architect の根拠による。** 不変ローカル ID（ADR-010）と
  版番号（ADR-005・009）は**既存記録へ遡及できず、後回しにすると剥がせない結合になる**。
  これは architect の拒否権に該当する。
  一方、構造条件は**作り方の縛りであって機能追加ではない**ため、builder の工数懸念とは衝突しない。
- レシピ3件としたのは qa-sec の「**検証枠がレシピ件数に線形比例する**」による。
  プロトタイプで確かめたいのは中身が刺さるかであって、件数の多さではない。
  手順数を変えるのは architect の条件で、データ構造の可変性を示すためである。
- 検証手段は builder の指摘による。Windows から Safari 実機デバッガが使えない以上、
  画面内ログ表示以外に受入条件を確かめる手段がない。
- 検証不能条件の書き換えは qa-sec による。特に「権限ダイアログが表示されない」は
  **不在の証明**であり、grep による静的確認と実機完走の組み合わせに置き換えなければ条件化できない。

## 却下した案とその理由

- **A（20項目すべてを必須）**: 実装資産ゼロで工数超過（builder）。5体中支持ゼロ。
- **C（機内モードでの中心機能完走のみを必須）**: charter 成功条件2・3 を落とす（pm）。
  ADR-003・010 の復旧手段を落とすとストレージ消去で評価そのものが飛ぶ（builder）。
  ADR-008 の「一覧が空疎」を評価者から確かめられず、出す意味が消える（user-advocate）。
  architect が明示的に反対した。
- **レシピ6件（pm 案）**: pm は「ADR-009 の**レシピが尽きる時期の観察**が成立する最小」を根拠とした。
  この根拠は失当ではなく、**3件を採ったことで ADR-009 の観察項目が犠牲になる**（下記「影響範囲」に引き継ぐ）。
- **レシピ5件（builder 案）・8件（user-advocate 案）**: 検証枠の線形増加を優先して却下。
  なお builder は「1件6手順以内」を上限として示した。これは必須3件の設計時に参考とする。

## 影響範囲

- **フェーズ1（要件整理）はこの ADR で完了する。** 次は /spec による仕様書生成である。
- **/spec の生成規則に条件が付いた。** 推奨枠の条件も受入条件として記載し、必須／推奨を明示すること。
  これは qa-sec が最大リスクに挙げた「**推奨枠に落ちた条件が /spec で受入条件から消え、
  未検証のまま完了扱いされる**」への対処である。
- **ADR-009 の観察項目が犠牲になった。** レシピ3件では「尽きる時期」の観察が成立しない
  （pm は最小6件とした）。**プロトタイプ評価では「尽きるまでの時間」ではなく
  「3件を作り切ったか、作り切る気になったか」を観察対象に切り替える。**
- **ADR-007 の執筆工数が確定した。** 3件・変わり種1件・手順数を変える。
  builder の示した「1件6手順以内」を設計の目安とする。
  ADR-001 で builder が挙げた「執筆工数の膨張」リスクは、件数を絞ることで抑えた。
- **V1・V2 が未検証のまま残る。** architect が最大リスクに挙げたとおり、
  **V1（PWA ストレージ消去条件）・V2（Wake Lock の安定性）が未検証のまま ADR-003 の前提が崩れる**可能性がある。
  本 ADR の必須条件1（機内モード完走）と、書き換え後の「Safari 手動消去で再定義」は、
  いずれも V1・V2 の結果に依存する。**フェーズ2の技術調査で先に潰すこと。**
- **推奨枠に落ちた条件のうち、次は評価への影響が大きい**（各体が最大リスクとして指摘）。
  - 記録一覧と初期値3ケース（pm）— 落ちると ADR-008 の「一覧が空疎」検証が評価に間に合わない
  - エクスポートを促す導線（user-advocate）— 粗いと評価が中身でなく煩わしさに向く
  これらは推奨だが、**実装順序としては優先すること。**
