# ADR-009: オンライン機能の境界

- 日付: 2026-09-11
- 状態: 採択

## 論点

オンライン機能を入れるか。入れるなら charter 目的2 が言う「付加価値」の境界はどこか。
PWA である以上アプリ本体の配信と更新には通信が要るため、それを「オンライン機能」に数えるかという
境界の定義も含む。

## 決定

**機能としてのオンライン要素は入れない。**

- **通信はアプリ本体の配信・更新のみ**とする。**これはオンライン機能に数えない。**
- **記録の共有・端末間移送は入れない。** 端末間移行は ADR-003 のエクスポート／インポートで充足済みである。
- **レシピの追加取得は現フェーズでは入れない。** レシピの増補は**本体更新に同梱して配る**。

ただし、将来の追加取得を閉ざさないため構造を先に縛る。

- **同梱レシピは版番号付き静的データとしてコードから分離する。**
- **読込をポート化する。**

## 理由

- 人間の裁定による。5体中4体が A（オンライン要素ゼロ）を支持した。
- 記録の共有（C）は**5体全員が退けた**。pm が charter 非目標2（同期基盤）に該当するとして拒否権を行使し、
  architect・builder・qa-sec は ADR-005「外部送信ゼロ」への抵触を理由に反対した。
  端末間移行は ADR-003 のエクスポート／インポートで既に足りており、追加の利益がない
  （pm・user-advocate が独立に指摘）。
- レシピの追加取得（B）を却下した決め手は、**その利益が B なしで得られる**ことである。
  PWA では本体更新を Service Worker が自動で運ぶため、レシピを増やしたければ本体更新に同梱すれば届く。
  builder が「追加通信路なしで同梱追加でも済む」と明言した。
  B が足すのは利益ではなく**別の取得経路**であり、代償として qa-sec の言う受入条件不能
  （取得失敗・部分ダウンロード・改竄レシピ）と、architect の言うキャッシュ二系統化が乗る。
- A であれば charter 成功条件1「機内モードで全手順完走」を条件化できる（qa-sec）。
- 分離とポート化の条件は architect による。これにより B は後から足せる。

## 却下した案とその理由

- **C（記録の共有・端末間移送）**: charter 非目標2（サーバ側の恒常運用・同期基盤を作らない）に該当し、
  pm が拒否権を行使。ADR-005「外部送信はゼロ」にも正面から反する。
  さらに architect は「記録スキーマに同期 ID と衝突解決が侵入する剥がせない結合」を指摘した。
  端末間移行という目的自体は ADR-003 のエクスポート／インポートで充足済みである。
- **B（レシピの追加取得）**: 利益が本体更新で代替可能であるため、追加の取得経路を持つ理由がない。
  qa-sec は取得失敗・部分ダウンロード・改竄レシピの受入条件が書けないとし、
  builder は取得・版管理・SW キャッシュ整合・オフライン時フォールバック・同梱分とのマージが増えるとした。
  user-advocate のみが支持したが、**本人が最大リスクとして「新作が供給されず『更新のない更新機能』だけが残る」**
  を挙げている。すなわち B の空振りは通信経路の問題ではなく、ADR-007 で引き受けた執筆工数の問題である。
- **同梱レシピをコードに直書きする案**: ADR-001 で architect が挙げた条件
  「レシピ・手順をコードに直書きせず、データ層と表示層を分離すること」に反する。本 ADR で分離を確定させた。

## 影響範囲

- **ADR-001 の architect 条件が確定した。** 「レシピ・手順をコードに直書きせず、データ層と表示層を分離する」は、
  本 ADR の「版番号付き静的データとしてコードから分離し、読込をポート化する」として具体化された。
- **ADR-007 との関係**: レシピの増補手段は**本体更新への同梱**である。新作を届けるには本体を更新して配る。
  これは通信経路の問題ではなく執筆工数の問題であり、**Q9 の見積り対象**として既に上がっている。
- **charter 目的2 の「付加価値としての通信」は、現フェーズでは行使しない。** 通信は本体の配信・更新にのみ使う。
- **Q9（MVP 完了定義）**: 受入条件に以下を追加する。
  - **機内モードで、同梱レシピの選択から手順完走・記録までが最初から最後まで通ること**（charter 成功条件1 の具体化）
  - **Service Worker 更新後に、旧版と新版のレシピが混在しないこと**（qa-sec・builder・architect が共通して挙げたリスク）
  - レシピデータの版番号が、インポートした記録の版番号と独立して扱えること
- **Q8（エクスポート／インポート）**: 記録の共有が入らないため、エクスポートの用途は
  「同一利用者の端末内バックアップと復旧」に限定される。他人へ渡す想定は置かない。
- **持ち越した懸念**: pm が最大リスクとして挙げた「**同梱レシピが尽きた時に更新手段を持たず、
  目的1の長期利用が頭打ちになる**」は解消していない。user-advocate が B を支持した理由と同じ問題である。
  両者の差は手段の評価だけで、問題認識は一致していた。
  **本体更新でレシピを増補し続けられるかが、この懸念への唯一の答えである。**
  プロトタイプ評価で「同梱レシピを何件作り、どのくらいで尽きるか」を観察対象とする。
- 将来レシピの追加取得を足す場合は、qa-sec の受入条件3点（取得失敗・部分ダウンロード・改竄レシピ）と
  architect のキャッシュ系統整合を条件に含めたうえで、**新規 ADR を要する。**
