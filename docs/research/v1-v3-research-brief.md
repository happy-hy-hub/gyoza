### 前提

iPhone 向けアプリのプロトタイプを作る前の技術調査です。以下が確定しています。

- **配信は PWA**（GitHub Pages でホスティング、Safari で開いてホーム画面に追加）
- **完全オフラインで機能が成立すること**が要件。サーバは持たない
- **追加料金ゼロが必須制約**。Apple Developer Program（年$99）は使えない
- 開発は **Windows**。ローカルに Xcode は無い。デバッグは **iPhone 実機**
- データはすべて端末内に保持。外部送信はゼロ
- アプリは「調理中の手順ガイド＋タイマー」が中心機能。焼き終わりに記録を残す

詳細はフォルダ内の `docs/requirements/spec.md` と `docs/requirements/decisions/` を参照してください。

### 依頼

**V1・V2・V3 の3件を調査してください。互いに独立しているので、並列で進めて構いません。**

各項目について、**事実（出典付き）** と **推測** を明確に分けて書いてください。
出典は一次情報（Apple の公式ドキュメント、WebKit のブログ・バグトラッカー、W3C 仕様、MDN の対応表）を優先し、
個人ブログや Q&A サイトを根拠にする場合はその旨を明示してください。
**iOS のバージョンによる差があれば、どのバージョンからどう変わったかを明記してください。**

#### V1: ホーム画面に追加した PWA のストレージは、いつ消えるか

**問い**

1. ホーム画面に追加した Web アプリ（standalone モード）の IndexedDB / localStorage / Cache Storage は、
   どのような条件で OS または Safari に消去されますか。
2. Safari のタブで開いた場合と、ホーム画面に追加した場合とで、**扱いは異なりますか。**
   （「7日間未使用でスクリプト書き込みストレージが消える」という ITP のルールが、
   ホーム画面の Web アプリにも適用されるかを明確にしてください）
3. `navigator.storage.persist()` は iOS Safari で機能しますか。機能する場合、
   永続化の許可はどう判定され、許可されたストレージは消去対象から外れますか。
4. 保存できる容量の上限はいくつですか。上限に達した場合の挙動はどうなりますか。
5. アプリ側から「消去されたこと」を検知する手段はありますか。
6. 端末のストレージ逼迫時、iOS のバックアップ・復元時、Safari の履歴削除時の挙動はそれぞれどうなりますか。

**なぜ重要か**

この結果によって、記録データのエクスポート／インポート機能の位置づけが変わります。
消去が現実的に起きるなら「必須の復旧手段」、ほぼ起きないなら「単なる利便機能」です。
**現在の設計は前者を前提にしています。**

**成果物**

- 上記6問への回答（出典付き）
- **実機で確認する手順**（iPhone 上でストレージ消去を意図的に再現する方法。
  設定アプリからの操作、開発者向けの手段など。Windows から Safari の実機デバッガは使えない前提で）

#### V2: 前面表示のままタイマーを最後まで鳴らせるか

**問い**

1. **Screen Wake Lock API**（`navigator.wakeLock`）は iOS Safari で使えますか。
   どのバージョンから対応し、**ホーム画面に追加した standalone モードでも動作しますか。**
2. Wake Lock が**自動的に解除される条件**をすべて挙げてください
   （タブの非アクティブ化、アプリの切り替え、着信、低電力モード、画面の手動ロックなど）。
3. Wake Lock がかかっている間、iPhone の自動ロックは確実に抑止されますか。
4. 解除された場合、アプリ側で検知して再取得できますか。
5. 数分〜十数分の調理タイマーを、**画面を表示したまま最後まで動かし続けられますか。**
   実運用上の落とし穴があれば挙げてください。

**なぜ重要か**

バックグラウンドでの通知は使えないと判断済みです（Web Push はサーバが必要で、オフライン要件と衝突するため）。
そのため「**画面を表示したままなら確実に鳴る**」ことが唯一の成立条件になっています。
これが崩れると、配信経路そのものを選び直すことになります。

**成果物**

- 上記5問への回答（出典付き）
- **実機で検証する手順**（何分のタイマーを、どういう操作の組み合わせで試すか）

---

#### V3: そもそも iPhone で「音とバイブ」を鳴らせるか

**問い**

1. **`navigator.vibrate()`（Vibration API）は iOS Safari で使えますか。** 使えない場合、
   Web から iPhone を振動させる代替手段は存在しますか。
2. **端末のサイレントスイッチ（消音モード）がオンのとき、Web Audio や `<audio>` の音は鳴りますか。**
   鳴らせる条件があれば教えてください（AudioContext のカテゴリ設定など）。
3. iOS の自動再生制限のもとで、**タイマー満了時に音を鳴らす**にはどうすればよいですか。
   ユーザー操作を起点にした事前の音声解放が必要ですか。その解放はどのくらい持続しますか。
4. 音量が小さい／マナーモードという状況で、**利用者に確実に気づかせる手段**は Web に何かありますか。

**なぜ重要か**

「報知は音とバイブのみ」と決定済みですが、**この2つが iPhone の Web で実際に使えるかを確認していません。**
台所で手が離せない状況でタイマーに気づけないと、中心機能そのものが成立しません。

**成果物**

- 上記4問への回答（出典付き）
- **実機で検証する手順**

### 全体の成果物

1. **比較表（スプレッドシート）** — V1・V2・V3 の各問いについて「結論／根拠／出典 URL／iOS バージョン依存の有無／確度（確実・推定・不明）」
2. **実機検証手順書** — 3項目分をまとめた、上から順に実行できるチェックリスト形式
3. **判定サマリ（1ページ）** — 各項目が「成立」「条件付き成立」「不成立」のどれか。
   **不成立または条件付きの場合、何を作り直す必要があるかまで書いてください。**

### 注意

- 断定できないことは「不明」と書いてください。**推測を事実として書かないでください。**
- iOS のバージョンによって結論が変わる場合、**どのバージョンを前提に判断すべきかも提案してください。**
- 「PWA では無理だからネイティブにすべき」という結論になった場合も、そのまま書いてください。
  ただし追加料金ゼロという制約は動かせないので、その制約下での選択肢も併記してください。

## 結果の受け取り後にやること

1. 判定サマリを読み、各項目が成立したかを確認する
2. **不成立または条件付きの項目があれば、該当する論点を `/meeting` で再審議する**
   - V1 不成立 → ADR-003（エクスポートの位置づけ）
   - V2 不成立 → ADR-002・003（タイマー要件と配信経路）
   - V3 不成立 → ADR-008（報知手段）。**中心機能の成立性に直結する**
3. 裁定を `/decide` で ADR 化する
4. `/spec` を再実行して spec.md を再生成する
